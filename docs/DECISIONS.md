# Decisions

| # | Decision | Why | Trade-off / alternative rejected |
|---|---|---|---|
| 1 | Clean Architecture with 4 projects (Domain, Application, Infrastructure, Api) | Enforces a one-way dependency rule, keeps business rules and the AI/ranking logic testable in isolation from EF/HTTP | More project boilerplate than a single-project app; justified because the AI and crawler logic are the parts that most need isolated, fast unit tests |
| 2 | CQRS via MediatR (one handler per use case) | Small, single-responsibility handlers instead of fat services; consistent shape across the whole codebase for use cases that came from an AI-assisted, feature-by-feature workflow | Adds an indirection layer vs. calling services directly; rejected direct-service-call style because handlers keep validators, DTOs and logic co-located per use case |
| 3 | SQLite instead of SQL Server | The initial AI proposal (as a default ".NET stack" choice) was SQL Server; changed it deliberately — this is a local, single-user recruitment app, not an ERP-scale system, and SQLite needs no separate server, ships as a single file, and is trivial to reset between demos | Less suited to concurrent writers / large-scale production traffic; acceptable given the actual scale and deployment target |
| 4 | `DateTime` instead of `DateTimeOffset` on entities | SQLite (via EF Core's provider) does not sort `DateTimeOffset` columns correctly; recency filtering (last-24h window) depends on correct chronological sort | Loses explicit UTC-offset metadata on the value itself; mitigated by always storing/parsing in UTC and documenting the convention |
| 5 | TPH (Table-Per-Hierarchy) for `Vehicle`/`Car` | Adding a future category (e.g. `Motorcycle`) only needs a new subclass + enum value + source adapter, with zero changes to search/ranking/API/UI | TPH tables get wider as subtypes grow; acceptable for a handful of vehicle categories, not chosen for deep/complex hierarchies |
| 6 | LLM used only as a criteria extractor, never as the query executor | Keeps the app deterministic, explainable and safe: the model can't invent listings, can't run SQL, can't see the database | A "let the LLM browse the DB / call tools" agentic approach would be more flexible but far less predictable, harder to test and riskier |
| 7 | Deterministic C# ranking/scoring over an LLM-filtered candidate set | Hard filters run in SQL; soft-preference scoring and `matchReasons` are plain, readable, unit-testable C# — a reviewer can see exactly why a result was ranked where it is | An LLM-side re-ranking step would be more "clever" but non-reproducible and impossible to unit test reliably |
| 8 | OpenRouter as the LLM gateway | Single API key, access to multiple free-tier models, no need to manage several provider SDKs/keys | A direct OpenAI/Anthropic integration would mean provider lock-in and a paid-only model catalogue; OpenRouter's free tier fits a cost-conscious recruitment project |
| 9 | JWT bearer auth with `PasswordHasher<User>`, without the full ASP.NET Core Identity stack | The app needs login/register and per-user data scoping only — no roles, no email confirmation, no external login providers | Full Identity would add tables, migrations and concepts (roles, claims, external logins) that are pure overhead here |
| 10 | AngleSharp for HTML parsing | Mature, dependency-free .NET HTML/CSS-selector engine; no headless browser needed since the required data is present in server-rendered HTML (once you're on the detail page) | A headless browser (Playwright) would handle more dynamic pages but adds significant runtime cost/fragility for a page that doesn't need it |
| 11 | Detail-page-first crawl strategy (not just the list page) | otomoto's list page doesn't expose a reliable, immediately-available exact publish date — the "Published X ago" text is friendly but is evaluated client-side and isn't safe to parse for a 24h cutoff; the detail page has the exact date/time | Slower (one extra HTTP request per listing) and more load on the source site; accepted because correctness of the recency filter matters more than crawl speed here, mitigated by page caps and a request delay |
| 12 | Fixture-based crawler tests, no live HTTP in the test suite | Parser tests run against saved HTML files (`tests/AutoFinderAI.UnitTests/Fixtures/otomoto/`), so they're deterministic, fast, and don't depend on otomoto's availability or markup changing mid-run | Fixtures can go stale if otomoto changes its markup; accepted, and refreshing a fixture is cheap compared to flaky live-HTTP tests |
| 13 | No vector search / embeddings | The dataset is small (single-source, 24h-recency filtered) and criteria are structured attributes (price, year, mileage, fuel...), which suit exact/range SQL filters far better than semantic similarity | A vector-search layer would add infrastructure (embedding calls, a vector index) for a problem that structured filtering already solves well |
| 14 | Degraded mode when no OpenRouter key / OpenRouter unreachable | The app should never hard-fail just because a paid/rate-limited external dependency is unavailable; `/api/ai/status` reports `available:false` and the chat falls back to a narrow keyword search (Title/Make/Model only) | The fallback is intentionally limited (no fuzzy/semantic matching) to avoid guessing at intent without the LLM |
| 15 | Hard cap on ranking `limit` and SQL candidate set size | Protects against an LLM-suggested unbounded `limit` and against materializing the whole table before ranking | Slightly reduces flexibility for "show me everything" queries; acceptable, the UI can request more within the cap |
| 16 | One extraction call per user message, no tool-calling/agent loop | Keeps behaviour, latency and cost predictable and easy to reason about/test | A multi-step agent could handle more complex, multi-turn refinement automatically, but at the cost of predictability and testability that this project prioritizes |
| 17 | Repository split into 6 specialised AI agent roles instead of one general assistant | Matched each agent's ownership boundary to a layer/concern (see `docs/AI_WORKFLOW.md`), so review always happens from a fresh, adversarial perspective and no single pass both writes and grades the same code | Slower to set up than "just start prompting"; paid off given the project's breadth (backend, AI, frontend, tests, docs) in a short timeframe |
| 18 | Docker Compose with two services + a named volume for SQLite | One-command run for a reviewer with zero local tooling beyond Docker; the SQLite file survives `docker compose down` | Adds two Dockerfiles to maintain vs. "just run `dotnet run`"; both paths are documented in the README so neither is mandatory |
